Walkthrough of run.c

A guided tour of run.c, piece by piece, in the order you'll code it, so you can port it to any language. Each section gives you a one-sentence summary, an analogy, an example you can work out by hand, the commented C, and what to keep in mind for your port. No solution code here: writing it is your job.

Example: pointer arithmetic

Picture a flat array of 6 floats [a, b, c, d, e, f] and a float* p that points to a.

p + 2 points to c. (p + 2)[1] is d. All the weight loading relies on this: "the wq tensor starts here, the next one starts N floats further on".

Two lines not to misread

#pragma omp parallel for (lines 221, 283): a parallelism hint for OpenMP. With make run, it is ignored (not compiled with -fopenmp). For you: plain sequential code. Later, it is where you can add parallelism (threads, a thread pool...). Rust note: this is where rayon would go.

unsigned long long (lines 114, 249): an unsigned 64-bit integer, used so offset multiplications don't overflow on big models (13B+).

3. The big picture: main then generate

In one sentence

You build 3 objects (the model, the tokenizer, the sampler), then you run a loop: forward → pick the next token → print it → repeat, up to 256 tokens.

3.1 main: build the 3 objects

Default values (lines 909–917): tokenizer.bin, temperature 1.0, top-p 0.9, 256 steps, seed = the current time. With -t 0, the seed and top-p no longer matter. That is why the output becomes deterministic.

Note: vocab_size comes from the model, not from the tokenizer (Karpathy forgot to store it in tokenizer.bin, see his “sigh” on line 386).

3.2 generate: the loop

Analogy

A storyteller who only sees the last word they just said, plus their notes (the KV cache) on all the words before it. Each turn, they say just one more word. During the prompt, someone whispers the words to them: they “say” them without choosing.

Trace by hand

MVP case, no prompt: prompt_tokens = [1], so num_prompt_tokens = 1, and you sample from the very first turn.

With -i "Once upon": encode gives [1, 9038, 2501] (= BOS, “␣Once”, “␣upon”, checked in tokenizer.bin).

Three details to remember
  • forward gets only one token at a time, plus its position pos. The earlier tokens “live” in the KV cache.
  • Generation stops on BOS (1), not EOS (2): in TinyStories, every story starts with BOS.
  • The timer starts after the first turn (line 772): the tok/s figure counts pos − 1 tokens.
If you want to go further

During the prompt, run.c does a full forward per token and throws the logits away. This is exactly what prefill optimizes in a real server (process the whole prompt at once). Keep this in mind for later.

The negative vocab_size hack

At the end of the model, you need a “classifier” matrix that turns the 288-number vector into 32,000 scores. Many small models reuse the embedding table for this (same shape: 32000 × 288). The sign of vocab_size tells you which case you are in: positive = shared (stories15M), negative = a separate wcls matrix, stored at the end of the file.

Check it yourself

xxd -l 28 stories15M.bin shows the first 28 bytes. 288 = 0x120, so the first 4 bytes are 20 01 00 00 (little-endian: the lowest byte comes first).

For your port

Step 2 of the plan: read these 28 bytes, print them, and compare with the table above. Remember “little-endian” and “signed int32” (the sign matters, because of the hack).

5. The checkpoint: slicing one big array of floats

In one sentence

After the header, the file is just one long run of float32 values packed back to back, with no separators. memory_map_weights knows the order they are stored in, and puts a “bookmark” at the start of each tensor.

5.1 The recipe: how to compute each size

Two units, one rule

The formulas below give a number of floats (weights). Your file buffer is in bytes: one float = 4 bytes, so bytes = 4 × floats, both for the size and for the start position.

The Config fields are ingredients (“6 layers”, “288 cells”). Only their product is a size. Do all this math with 64-bit integers (e.g. usize in Rust, not i32): a 32-bit integer overflows past ~2.1 billion, which happens on big models (see the comment on line 113 of the C code).

Step 1: the derived values (compute these first)

NameFormulastories15M calculationValue
head_sizedim / n_heads288 / 648
kv_dimdim × n_kv_heads / n_heads288 × 6 / 6288
header size7 fields × 4 bytes7 × 428 bytes = 7 floats

Step 2: each tensor, in file order

The “Start” column is the cursor position before reading the tensor, counted from the very start of the file (header included). After each tensor, the cursor moves forward by “Num floats”.

The total lands exactly on the file size: 60,816,028 bytes. This is the final test for your loader: in both cases (shared or not), your cursor must end exactly at the end of the file. If it stops early or goes past the end, one of your formulas is wrong.

Three pitfalls
  • The order is not the order of the comments in the struct. In the file, rms_ffn_weight comes after wo. Follow memory_map_weights, not the struct.
  • The 2 RoPE gaps (lines 137–138): old precomputed arrays that are still in the file but no longer used. You must skip them, or wcls would be wrong (in unshared mode).
  • One tensor holds all the layers, one after another. wq = 6 matrices of 288×288 packed together. Layer l starts at wq + l*dim*dim (you will see this in forward).

How a matrix is stored

All matrices are stored row by row (row-major), with one row per output value. For w1: 768 rows (one per hidden neuron) of 288 numbers (one per input). The shape comments in the struct (lines 36–43) are not all written the same way round. Trust how matmul reads them instead (section 7).

mmap: why it is used, and why you don't need it

mmap (line 158) tells the OS: “act as if the file were already one big array in memory, and load the pages when I touch them”. The benefit: instant startup, no copy. For 60 MB, reading the whole file at once works just as well, and you avoid unsafe memory-mapping code. Line 160: *data + sizeof(Config)/sizeof(float) = skip 28/4 = 7 floats, which is the header.

For your port

Step 3 of the plan. Do it in two passes: (1) turn the bytes after the header into a list of little-endian float32 values, (2) slice that list in the exact order shown above. For the shared classifier, don't copy 37 MB: you just need to know that you read the embedding table at that point.

Simple test: print the first 5 floats of token_embedding_table and of rms_final_weight in your port and in C (add a printf to the C code), then compare.

7. The 3 building blocks: rmsnorm, softmax, matmul

In one sentence

All of forward is built from these three functions (plus a few simple loops). Write them and test them before forward.

7.1 rmsnorm — bring the vector back to the right scale

ParameterRoleIn the example below
xthe input: the vector to normalize (read only)[3, 4]
othe output (o): a box where the function writes the resultgets [0.849, 2.263]
weightthe tuning values, one per cell[1, 2]
sizethe length of the vectors2

A C habit: a function does not "return" an array. You give it a box to write into. matmul(xout, x, …) follows the same pattern. In forward: rmsnorm(s->xb, x, …) (line 252) reads the stream x and writes into the scratch buffer xb. x stays untouched for the residual.

Analogy

A volume control. Whether the vector arrives shouting (big numbers) or whispering, you bring it back to an "average volume" of 1. Then weight turns each cell up or down on its own (learned during training).

Example (seen before)

x = [3, 4], weight = [1, 2]

mean of squares = (9 + 16) / 2 = 12.5 (+ 1e-5, negligible here) 1 / √12.5 = 0.2828 normalized x = [3 × 0.2828, 4 × 0.2828] = [0.849, 1.131] × weight = [0.849 × 1, 1.131 × 2] = [0.849, 2.263]

RMSNorm vs LayerNorm (GPT-2): LayerNorm first subtracts the mean and adds a bias. RMSNorm only divides by the "average size" (RMS = root mean square). Simpler, and just as effective.

For your port

Line 357: rmsnorm(x, x, ...) uses the same buffer as input and output. C doesn't care, but some languages won't let you read and write the same buffer at once (Rust note: the borrow checker refuses it). Two options: an "in place" variant, or write into another buffer. Note that this is fine mathematically: the sum of squares is fully computed before the first write.

7.2 softmax — turn scores into percentages

Example
x = [1, 2, 3] − max (3) → [-2, -1, 0] exp → [0.1353, 0.3679, 1.0000] sum = 1.5032 ÷ sum → [0.0900, 0.2447, 0.6652] (total = 1)

Why subtract the max? The result is mathematically the same (it cancels out on top and bottom). But exp(1000) overflows in f32 (infinity), while exp(0) = 1. With the max at 0, the largest exp is always 1: no overflow.

Note: softmax works in place (it overwrites its input) and only touches the first size cells. In attention, size = pos + 1: only the tokens seen so far.

7.3 matmul — the function where all the time goes

Read the parameter order carefully: n = size of the input, d = size of the output. W has d rows of n numbers.

Analogy

W is d "detectors". Each detector (one row) looks at the whole input vector and gives a score (a dot product). The output = the list of d scores.

Example (d = 2, n = 3)
W = [[1, 2, 3], stored flat: w = [1, 2, 3, 4, 5, 6] [4, 5, 6]] x = [1, 0, 2] xout[0] = 1×1 + 2×0 + 3×2 = 7 w[0*3+0], w[0*3+1], w[0*3+2] xout[1] = 4×1 + 5×0 + 6×2 = 16 w[1*3+0], w[1*3+1], w[1*3+2]

The index i*n + j is the 2D version of the usual flat-array formula b*T*C + t*C + c: "skip i full rows, then move forward by j".

Where the compute goes for one token (stories15M)

Each weight is used exactly once per token (one multiply + one add). For this small model, the final classifier (32000 × 288) is ~61% of the work. On a 7B model, it would be a few %.

For your port

Before forward: write one test per building block, using the examples above (worked out by hand, so you know what to expect). For matmul, watch the (n, d) order: it is bug #1 in ports of run.c. A test with a non-square matrix (2×3) catches it right away; a square matrix does not.

8. forward: one token goes through the model

In one sentence

forward(token, pos) takes one token and its position, and returns 32,000 scores (the logits). There are 12 steps: step 1 runs once, steps 2 to 10 are repeated 6 times (once per layer l), and steps 11 and 12 run once.

8.0 Reminder: the dimensions

The key points:

  • Everywhere: W · x = result, with W = (size of result) × (size of x). E.g. (768×288) · (288×1) = (768×1).
  • Each layer has its own W, stored one after the other. "W[l]" in this section = the W of layer l, which starts at l × (size of one W).
  • The norms are not W matrices: one tuning value per cell (288 per layer), multiplied cell by cell.

Step 1 — Embedding

What it does: copy the token's row into x. No math.

x = token_embeddings, cells token×288 to (token+1)×288
For your port

Copy into x (it already exists). Do not allocate a new array. Check: token = 0 → x starts with −0.059825, −0.014561, 0.106149.

No position is added here (unlike GPT-2). The position comes in at step 4 (RoPE).

Step 2 — Norm before attention

What it does: bring x back to a standard "volume", in the scratch buffer. x stays untouched: you need it at step 6.

scratch = rmsnorm(x, attention_norm[l]) attention_norm[l] = cells l×288 to (l+1)×288

Step 3 — Make q, k, v (and fill the cache)

What it does: three W · x on the same scratch. The k and v results go straight into the KV cache.

q = attention_query[l] · scratch (288×288)·(288×1) = 288×1 key_cache[l][pos] = attention_key[l] · scratch (288×288)·(288×1) = 288×1 value_cache[l][pos]= attention_value[l] · scratch (288×288)·(288×1) = 288×1
Analogy (the meeting)

q = the question the token asks. k = its badge. v = what it has to say if someone comes to it. The KV cache is the register: one page per layer, one row per seat (pos). Each token writes its row once and never rewrites it.

Where is row [l][pos]? The cache is laid out as [layer][position][288]:

start of key_cache[l][pos] = l × 256 × 288 + pos × 288

For your port

In the C, s->k and s->v are pointers into the cache row (not separate buffers). In your code: compute the start of the row (a number), and pass the slice key_cache[start .. start + 288] directly as the matmul output.

For stories15M, k and v have 288 values. On a model with GQA, they have kv_dim values (smaller): use kv_dim, not 288.

Step 4 — RoPE: give q and k their position

What it does: rotate q and the k you just wrote (key_cache[l][pos]) by an angle that depends on pos. v is not touched. Result: the q·k score (step 5) depends on the distance between the two tokens.

a) A pair of numbers = an arrow. Split the vector into pairs (cells 0-1, 2-3, …). To rotate the arrow (v0, v1) by an angle θ:

v0' = v0 × cos θ − v1 × sin θ v1' = v0 × sin θ + v1 × cos θ

E.g. the arrow (1, 0) rotated by 90° becomes (0, 1).

b) The angle = pos × freq. At token 0 there is no rotation. At token 5, you rotate by 5 notches.

c) Each pair has its own speed. Inside a head (48 cells = 24 pairs), pair 0 turns fast and the last pair turns very slowly:

freq = 1 / 10000^(head_dim / head_size) head_dim = 0, 2, 4, … , 46
Example: head_size = 4 (2 pairs), pos = 1
pair 0: freq = 1/10000^(0/4) = 1 → angle 1 rad pair 1: freq = 1/10000^(2/4) = 0.01 → angle 0.01 rad q = [1, 0, 1, 0] → [cos 1, sin 1, cos 0.01, sin 0.01] = [0.5403, 0.8415, 0.99995, 0.0100]

d) Why "relative". q is rotated by m×θ, k by n×θ: their product only sees the gap (m − n)×θ.

m = 3, n = 1 → gap 2 → q·k = cos 2 = −0.416 m = 5, n = 3 → gap 2 → q·k = cos 2 = −0.416 same score

Play with RoPE (one pair)



Keep the same gap between m and n: the score does not change.

  • The loop walks the 288 cells of q two at a time. i % head_size = the position inside the head: each head starts again at pair 0.
  • rotn: if k is shorter than q (GQA), past kv_dim only q is rotated. For stories15M: always both.
  • So the cache stores k vectors that are already rotated. Old ones are never rotated again.
  • The pairs are neighboring cells (i, i+1). Hugging Face pairs them differently (i and i + 24): do not mix the two.
For your port

Same formula, in float32, in the same order as the C. Convert pos to float32 for the multiplication. An error of 1e-6 here can change an argmax later.

Heads are just a way of slicing. The 288 cells of q (and of each cache row) are cut into 6 slices of 48:

No causal mask

In picoGPT, the future is masked with −∞. Here the loop stops at t ≤ pos, and the future is not in the cache yet: the mask is implicit.

att is 6 × 256: one row of 256 per head, but only pos + 1 cells are used. Row h starts at h × 256.

GQA: h / kv_mul

On some models, several q heads share the same k/v slice (this makes the cache smaller). The k/v slice to read for head h is h / kv_mul (integer division):

4 q heads, 2 kv heads → kv_mul = 2: q0, q1 → kv 0 q2, q3 → kv 1

For stories15M, kv_mul = 1 (head h → slice h). Write it with h / kv_mul anyway.

For your port
  • Reset slice h of scratch to zero before 5c (line 308, memset): you add into it.
  • You read the cache and write to att and scratch. These are separate fields of RunState. Rust note: borrow them separately.

Step 6 — Attention output + residual

What it does: mix the notes of the 6 heads with one W, then add them to x (you staple your notes onto the token's sheet, you do not replace it).

attention_out = attention_output[l] · scratch (288×288)·(288×1) = 288×1 x = x + attention_out (cell by cell)
Residual example
x = [1, 2], attention_out = [0.5, −1] → x = [1.5, 1]

Step 7 — Norm before the feed-forward

What it does: same as step 2, with different weights. x stays untouched (for step 10).

scratch = rmsnorm(x, ffn_norm[l])

Step 8 — gate and up: widen to 768

What it does: two W · x on the same scratch, going from 288 to 768.

hb = ffn_gate[l] · scratch (768×288)·(288×1) = 768×1 hb2 = ffn_up[l] · scratch (768×288)·(288×1) = 768×1

Step 9 — SwiGLU: combine gate and up

What it does: for each of the 768 cells: hb[i] = silu(hb[i]) × hb2[i]. No W, just cell by cell.

silu: silu(z) = z × sigmoid(z), with sigmoid(z) = 1 / (1 + e^(−z)). Roughly: keep positive values, squash negative values toward 0 (gently).

Analogy

gate (after silu) = how far to open the tap; up = the water. You keep "opening × water".

Example: 2 cells instead of 768
hb = [2, −1] hb2 = [3, 4] silu(2) = 2 × 0.881 = 1.762 silu(−1) = −1 × 0.269 = −0.269 hb = [1.762 × 3, −0.269 × 4] = [5.285, −1.076]

Step 10 — down + residual: back to 288

What it does: one W that brings 768 back down to 288, then you add it to x.

scratch = ffn_down[l] · hb (288×768)·(768×1) = 288×1 x = x + scratch
Two pitfalls

In the down matmul, n = 768 and d = 288: the reverse of gate/up.

In the file the order is gate, down, up (w1, w2, w3). But in the computation, gate and up go together, and down comes after.

Then go back to step 2 with the next layer (l + 1), up to l = 5.

Step 11 — Final norm

What it does: one last norm, after the 6 layers.

scratch = rmsnorm(x, final_norm)

The C writes rmsnorm(x, x, …) (in place). Writing into scratch gives the same result: the normalized x is only used at step 12. Rust note: this also avoids a borrow problem (reading and writing x at once).

Step 12 — Logits

What it does: a W with 32,000 rows: one score per possible token.

logits = lm_head · scratch (32000×288)·(288×1) = 32000×1

If lm_head is missing (None/null, as in stories15M), use token_embeddings instead (same shape 32000×288). forward returns logits.

9. The sampler: choosing the next token

In one sentence

With -t 0: take the highest score (argmax). Otherwise: divide by the temperature, apply softmax, and sample.

9.1 argmax MVP

Line 590: walk through the 32,000 scores and keep the index of the largest one. No softmax needed: softmax does not change the order. On a tie, the C code keeps the first one (strict comparison >). Do the same.

9.2 Temperature later

Divide the logits by T before softmax. T < 1: the gaps grow (safer, more repetitive). T > 1: the gaps shrink (more creative, wilder).

9.3 sample_mult: sampling later

Example
probs = [0.1, 0.6, 0.3] cumulative = [0.1, 0.7, 1.0] coin = 0.65 → first cumulative > 0.65 → index 1 coin = 0.05 → index 0

Analogy: a lottery wheel where each token gets a slice proportional to its probability.

The randomness comes from random_u32 (line 680): a xorshift, with 3 shifts + XOR + one multiplication. If you copy it bit for bit (with the same types: unsigned 64-bit integer, and a multiplication that overflows by wrapping around), you can even match the C output with -t 1 -s 42.

9.4 top-p later

Sort the tokens by probability, highest first. Keep the most likely ones until their total goes past p (0.9 by default). Then sample among them. The cutoff trick (line 634) drops, in advance, the tokens too small to ever make the cut. That way there is less to sort.

10. The tokenizer: numbers ↔ text

In one sentence

tokenizer.bin is a table of 32,000 pieces of text (each with a score). decode = read cell number id. encode = the reverse, but more complex (BPE).

10.1 The tokenizer.bin format MVP

[int32 max_token_length = 27] then 32,000 times: [f32 score] [int32 len] [len bytes of text, no \0]

A few real entries:

The texts are bytes (UTF-8), not always full characters. One emoji can be split across several tokens.

10.2 decode MVP

  1. Take the token's text.
  2. If the previous token is BOS and the text starts with a space → remove that space (piece++ = move forward one character). That is why the story starts with "Once" and not "␣Once".
  3. If the text looks like <0xXX> → replace it with the real byte XX. E.g. <0x0A> → a real newline.

safe_printf (line 431): if the piece is 1 byte and is neither a printable character nor whitespace, it is not printed.

For your port

To match the C byte for byte, keep tokens as bytes and write bytes to the output. If you turn them into your language's string type, a token that holds half of a UTF-8 character will cause trouble. Rust note: this applies to String; use Vec<u8> and write raw bytes. To compare: ./run stories15M.bin -t 0 > ref.txt, then diff it with your output (the tok/s line goes to stderr, so it does not get in the way).

10.3 encode: BPE later

Only needed with a prompt. The idea in 3 steps:

  1. BOS, then a "dummy" space before the text, then each UTF-8 character becomes a token (or its raw bytes, id = byte + 3, if it is not in the vocab).
  2. Repeat: among all neighboring pairs, find the one whose concatenation is in the vocab with the best score, and merge it.
  3. Stop when no pair can be merged anymore.
Real example: "Once" (scores read from tokenizer.bin)
start [␣] [O] [n] [c] [e] candidates ␣O (−179) On (−2692) nc (−17349) ce (−87) → best: ce [␣] [O] [n] [ce] → ␣O (−179) [␣O] [n] [ce] → ␣On (−1292) [␣On] [ce] → ␣Once (−8779) [␣Once] = id 9038

The vocab is sorted once (qsort) so strings can be found by binary search (bsearch). In most languages, a hash map from text → id does the same job.

A performance note that will help you in interviews

For each token, you read all the weights once (15.2 million floats ≈ 61 MB) and do only one multiply-add per weight read. So you spend more time bringing numbers in from memory than computing. Decoding is limited by memory bandwidth (memory-bound). At 218 tok/s, that is already ~13 GB/s of reads. This is the deep reason for batching: serve several requests with a single read of the weights. If you want to go further, this leads straight to continuous batching.

12. Interview questions (hide the answer, try first)

Why a KV cache? What would you recompute without it?

The keys and values of a past token never change (the future does not affect them). Without a cache, for each new token you would run the whole sequence through the model again to recompute them. That cost grows with the length, at every step. With the cache: one token per step, and you just reread the stored k/v.

Where is the causal mask in run.c?

Nowhere: you only handle one query at a time (the last token), and the loop stops at t <= pos. The future does not exist yet.

Why subtract the max in softmax?

To keep exp from overflowing in f32. The result is mathematically the same, because the factor e^(−max) cancels out on top and bottom.

How big is the KV cache for stories15M? And with GQA?

2 (k and v) × 6 layers × 256 positions × 288 × 4 bytes = 3.54 MB. With kv_mul = 2, kv_dim is halved, so the cache is too. On large models and long sequences, the cache is what limits the number of concurrent requests → PagedAttention.

Why is RoPE a "relative" encoding?

q is rotated by m·θ, k by n·θ; their dot product depends only on (m − n)·θ. The model sees distances, not absolute positions.

RMSNorm vs LayerNorm?

LayerNorm: subtract the mean, divide by the standard deviation, × gain + bias. RMSNorm: divide by the root of the mean of the squares, × gain. No centering, no bias, less computation.

Why is decoding memory-bound?

Each weight is read once per token and used for only one multiply-add. The chip waits on memory more than it computes. Batching several requests reuses each weight read several times.

What happens during the prompt in run.c, and why is it inefficient?

One forward per prompt token, and the logits are thrown away. A server does a prefill: the whole prompt in one pass (matrix × matrix matmul instead of matrix × vector). That is much more efficient because it is compute-bound.

Why is -t 0 deterministic even without setting the seed?

With temperature 0, sample() does an argmax and never calls the random number generator.

What is the sign of vocab_size for?

Positive: the classifier reuses the embedding table. Negative: a separate wcls matrix is stored at the end of the file (after the 2 old RoPE arrays, which you skip).
